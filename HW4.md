# ДЗ 4 — тесты для сервиса сокращения ссылок

Тесты лежат в `tests/`, рядом с `src/` из ДЗ 3. Для обычных тестов используются
pytest и HTTPX, для проверки под нагрузкой — Locust.

## Как запустить тесты

Команды нужно выполнять из папки, где лежит этот файл:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest tests
```

Отдельно запускать API и Redis не нужно. Для каждого теста создаётся временная SQLite БД, а вместо Redis используется fakeredis. Рабочие данные приложения при этом не меняются.

Запуск с подсчётом покрытия:

```bash
python -m coverage run -m pytest tests --junitxml=reports/pytest.xml
python -m coverage report
python -m coverage html
python -m coverage json
python -m coverage report --format=markdown > reports/coverage-summary.md
```

## Что проверяется

Тесты разделены на четыре файла:

- `test_api.py` — регистрация и вход, права на изменение ссылок, создание, обновление, удаление, поиск и статистика. Также проверяются неверные данные, совпадение сгенерированных кодов, одновременные переходы и сохранность данных после перезапуска.
- `test_expiration.py` — истечение срока ссылки, освобождение alias и фоновая очистка. Здесь же проверяется, что очистка продолжает работать после ошибки БД.
- `test_cache.py` — чтение и запись кэша, TTL, удаление ключей и обработка повреждённых данных или ошибок Redis.
- `test_config.py` — настройки приложения, секрет для JWT и часовые пояса.

Запросы отправляются через FastAPI `TestClient`. Для проверки одновременных переходов используется `httpx.AsyncClient`: после 24 запросов счётчик должен увеличиться ровно на 24.

Ошибки БД и Redis подставляются через `unittest.mock` и `monkeypatch`. Например, есть проверка, что после изменения ссылки старое значение в Redis не приведёт к редиректу на прежний адрес.

Чтобы тесты на срок действия не ждали целую минуту, `expires_at` в тестовой БД меняется на время в прошлом. Интервал фоновой очистки в одном из тестов уменьшен до 0.02 с. В самом приложении он остался равным 5 секундам.

## Нагрузочные тесты

Здесь нужен настоящий Redis. Проверить, запущен ли он, можно командой `redis-cli ping`. Если в ответ нет `PONG`, запускаем в отдельном терминале:

```bash
redis-server --bind 127.0.0.1 --port 6379 --save '' --appendonly no
```

Затем:

```bash
python load_tests/run_load.py --seconds 20 --repeats 3 --users 20
```

Скрипт сам запускает отдельный экземпляр API на свободном локальном порту, создаёт временную БД и после проверки останавливает процесс. Для Redis используется DB 14 и отдельные ключи для каждого запуска. Адрес можно поменять через `--redis-url`.

В Locust два сценария: массовое создание ссылок и переходы по уже созданным. Каждый запуск длится 20 секунд, одновременно работают до 20 пользователей. Для редиректов заранее создаются 64 ссылки и заполняется кэш. Затем выполняются по три запуска с кэшем и без него. Порядок чередуется, чтобы он меньше влиял на результат. Режим без кэша задаётся только в `load_tests/serve.py`, основной код приложения для этого не менялся.

Редиректы проверяются по коду 307 и заголовку `Location`, переходов на внешние сайты нет. После нагрузки сравниваются число созданных записей и сумма переходов в БД с итоговыми счётчиками Locust.

## Что получилось под нагрузкой

Всего выполнено 164 679 запросов без ошибок**. Число записей и переходов в БД совпало с количеством завершённых запросов.

| Сценарий | Запросов в секунду |
| --- | ---: |
| Создание ссылок | 1162 |
| Редиректы с кэшем, медиана трёх запусков | 1050 |
| Редиректы без кэша, медиана трёх запусков | 1286 |

В этих прогонах кэш не ускорил редиректы. При каждом переходе всё равно обновляется счётчик в SQLite, а Redis добавляет ещё одно обращение. Средняя задержка тоже была выше с кэшем: медиана по трём запускам составила 18.43 мс против 15.07 мс без кэша.

Это короткие локальные измерения: Locust, API и Redis работали на одном компьютере. Делать по ним вывод о производительности на Render нельзя, вариант с PostgreSQL здесь не проверялся.
